# v0.2 CLI Architecture — Study and Plan

**Status:** Draft, pending review by Alexandre Alvaro
**Date:** 2026-05-08
**Supersedes:** the v0.1.0-beta.1 architecture (CLI-as-prompt-printer)

This document captures the research and design for the v0.2 of `@alexandrealvaro/agentic`. It is the source of truth for what we are about to implement and why. Architectural decisions here are also recorded as ADRs under [`doc/adr/`](adr/) for traceability.

## Goal

Replace the v0.1 model (CLI prints a prompt, user pastes into agent) with a two-phase model that doesn't reinvent UX the agents already provide:

1. **CLI prepares the project** — install skills into the agent's native location, scaffold dotfiles.
2. **Agent runs the work** — user invokes `/agentic-bootstrap`, `/agentic-architecture`, etc. inside Claude Code or Codex; the agent does the interview and writes the artifacts.

The kit retains its DNA (lean, spec-driven, validated patterns from [WORKFLOW.md](../WORKFLOW.md)) but stops competing with the agent's own conversational interface.

## Terminology

| Term | Meaning here |
| --- | --- |
| Install | Putting the CLI on a user's machine (`npm install -g`, `npx`). Out of scope; npm handles it. |
| **Init** | The CLI command (`agentic init`) that prepares a project for the kit. Convention: `npm init`, `git init`, `terraform init`, `cargo init`, `specify init`. |
| Bootstrap | The agent-side skill (`/agentic-bootstrap`) that interviews the user and generates AGENTS.md. Distinct verb to avoid clashing with `init`. |
| Onboarding | The combined experience (init + bootstrap). UX concept, not a CLI verb. |
| Setup | Avoided. Ambiguous in the wild. |

Source: [CLI Guidelines (clig.dev)](https://clig.dev/) — *"Follow patterns that already exist."*

## Architecture

### Phase 1 — `agentic init` (CLI, filesystem ops)

```
$ agentic init

┌  agentic init  v0.2.0-beta.1
│
◇  Detected:
│    Stack: Node + React (package.json, *.tsx)
│    Mode: brownfield (code exists, no AGENTS.md)
│    Agents present: Claude Code (.claude/ found)
│
◆  Install skills for which agent(s)?
│  ● Claude Code
│  ○ Codex
│  ○ Both
│
◆  Skills:
│  [x] agentic-bootstrap        always
│  [x] agentic-architecture     always
│  [x] agentic-adr              always
│  [x] agentic-audit            always
│  [x] agentic-design           detected: frontend
│  [x] agentic-subagent         detected: Claude Code
│  [ ] agentic-skill            opt-in (rarely needed)
│
◆  Confirm? [Y/n]
│
◇  Installing…
│  + .claude/skills/agentic-bootstrap/SKILL.md
│  + .claude/skills/agentic-architecture/SKILL.md
│  …
│  + CLAUDE.md  (created, lists installed skills)
│
└  Done. Run `/agentic-bootstrap` in Claude Code to generate AGENTS.md.
```

Behavior:
- Auto-detect mode (greenfield / brownfield / audit) by inspecting cwd.
- Auto-detect features (frontend, backend, package manager) by inspecting manifest files.
- Auto-detect agent presence (`.claude/`, `.openai/`, etc.) and propose defaults.
- TUI for confirmation only — does not collect content (that is the agent's job).
- Idempotent: re-running on an already-initialized project does not duplicate; it surfaces a diff and asks per item.

### Phase 2 — Skills inside the agent

Skills are small markdown files with frontmatter that the agent loads automatically. Each generates one artifact through a multi-turn interview, leveraging the agent's native conversational UI.

| Skill | Generates | Agent invocation | Branch (Claude / Codex) |
| --- | --- | --- | --- |
| `agentic-bootstrap` | `AGENTS.md` at repo root | `/agentic-bootstrap` | both |
| `agentic-architecture` | `ARCHITECTURE.md` at repo root | `/agentic-architecture` | both |
| `agentic-adr` | `doc/adr/NNNN-<title>.md` | `/agentic-adr "title"` | both |
| `agentic-design` | `DESIGN.md` at repo root | `/agentic-design` | both, frontend only |
| `agentic-skill` | `.claude/skills/<name>/SKILL.md` (or equivalent) | `/agentic-skill <name>` | both |
| `agentic-subagent` | `.claude/agents/<name>.md` | `/agentic-subagent <name>` | Claude Code only |
| `agentic-audit` | drift report (no file written) | `/agentic-audit <artifact>` | both |

Each skill embeds the corresponding template content (from this kit's `templates/`) so the agent has everything it needs without reading external files.

## Skill source tree (in this repo)

```
src/skills/
├── claude-code/
│   ├── agentic-bootstrap/SKILL.md
│   ├── agentic-architecture/SKILL.md
│   ├── agentic-adr/SKILL.md
│   ├── agentic-design/SKILL.md
│   ├── agentic-skill/SKILL.md
│   ├── agentic-subagent/SKILL.md
│   └── agentic-audit/SKILL.md
└── codex/
    ├── agentic-bootstrap/{SKILL.md, agents/openai.yaml}
    ├── agentic-architecture/{SKILL.md, agents/openai.yaml}
    ├── agentic-adr/{SKILL.md, agents/openai.yaml}
    ├── agentic-design/{SKILL.md, agents/openai.yaml}
    ├── agentic-skill/{SKILL.md, agents/openai.yaml}
    └── agentic-audit/{SKILL.md, agents/openai.yaml}
```

Format differences per agent (validated by inspecting [cc-sdd](https://github.com/gotalab/cc-sdd) source):

| | Claude Code | Codex |
| --- | --- | --- |
| Path in target | `.claude/skills/<name>/SKILL.md` | `.agents/skills/<name>/SKILL.md` |
| Frontmatter | `name`, `description`, `allowed-tools`, `argument-hint` | `name`, `description` (minimal) |
| Body style | Markdown headings (`## When to Use`) | XML tags (`<instructions>`, `<background_information>`) |
| Extra files | none | `agents/openai.yaml` with `interface` and `policy` blocks |
| Root doc | `CLAUDE.md` | `AGENTS.md` (also informs agent the skills exist) |

Two source trees, some duplication accepted, install-time copy by agent. cc-sdd makes the same trade-off for the same reason.

## Auto-discovery rules

### Mode detection (already in v0.1)

| Signal | Mode |
| --- | --- |
| Empty dir (only trivial files) | greenfield |
| Has code, no `AGENTS.md` | brownfield |
| Has `AGENTS.md` | audit |

### Feature detection (new in v0.2)

| Signal | Effect |
| --- | --- |
| `package.json` deps include React/Vue/Svelte/Solid | enable `agentic-design` |
| Existence of `*.tsx` or `*.jsx` | enable `agentic-design` |
| Existence of `tailwind.config.*` or `tokens.json` | enable `agentic-design` (priority) |
| Existence of `.claude/` | enable `agentic-subagent`, default Claude Code |
| Existence of `.openai/` or `~/.codex` config in user env | default Codex |
| `Cargo.toml` / `go.mod` / `pyproject.toml` / `package.json` | always install required skills |

Detection is informative, not prescriptive. The TUI shows what was inferred; the user confirms or overrides.

References: [Vercel framework auto-detection](https://vercel.com/docs/builds/configure-a-build), [Snyk `--all-projects`](https://docs.snyk.io/snyk-cli/commands/test), [Laravel package auto-discovery](https://laravel-news.com/package-auto-discovery).

## Validation strategy

Three test layers (per [Joyee Goldberg's Node testing best practices](https://github.com/goldbergyoni/nodejs-testing-best-practices) and [Andrés Zorro on CLI integration tests](https://medium.com/@zorrodg/integration-tests-on-node-js-cli-part-1-why-and-how-fa5b1ba552fe)):

1. **Unit** — `detectMode`, `detectFeatures`, render functions. Pure inputs/outputs. Vitest.
2. **Integration** — spawn the CLI inside `mktemp` directories simulating each scenario:
   - Empty dir → greenfield, only required skills installed.
   - Node + React → frontend-aware, `agentic-design` included.
   - Existing `AGENTS.md` → audit mode, no overwrite.
   - Re-run on installed project → idempotent.
3. **TUI** — mock `@clack/prompts` selectors; snapshot what the user would see. Catches regressions in copy and flow.

Manual end-to-end stays primary for now: Alexandre runs on real projects, files issues. Automated coverage grows from those cases.

## Dogfooding plan

The kit applies its own rules to itself. Before any v0.2 code lands, the `agentic-development` repo gets:

1. **`AGENTS.md`** at the repo root — operational guide for any agent working on the kit (including me, Claude, in future sessions).
2. **`ARCHITECTURE.md`** at the repo root — describes the current CLI structure (commands, lib modules, skills source layout).
3. **`doc/adr/0001…0003`** — the three ADRs that complement this plan.
4. **`doc/v0.2-cli-plan.md`** — this document.

After v0.2 ships, we re-run `agentic init` on this repo and confirm it produces the same files (or a clean drift report). If it does not, the kit fails its own test before reaching anyone else.

This loop is the §14 of [WORKFLOW.md](../WORKFLOW.md): staged spikes with golden fixtures. The fixture is the repo itself.

## Implementation chunks

Each chunk is independently reviewable and shippable.

| Chunk | Scope | Output |
| --- | --- | --- |
| 0 | This plan + 3 ADRs + AGENTS.md/ARCHITECTURE.md for the repo | Files in `doc/` + repo root |
| 1 | `src/skills/` tree with `agentic-bootstrap` only, install logic, basic TUI, integration test | `agentic init` works for AGENTS.md generation in both Claude Code and Codex |
| 2 | Add `agentic-architecture`, `agentic-adr`, `agentic-audit` (the universal skills) | Coverage of core artifacts |
| 3 | Add `agentic-design`, `agentic-subagent`, `agentic-skill` (conditional skills) + feature detection | Full skill set |
| 4 | Polish: idempotency check, root doc append/create, README rewrite, version bump to `0.2.0-beta.1`, npm publish | Public release |

Each chunk produces tests before merging. No chunk merges into `main` until all four are done — `cli` branch holds the v0.2 work in progress.

## Open questions / decisions pending

These are flagged here so we don't lose them:

- **Root doc for Codex:** if a project already has an `AGENTS.md` (e.g., from v0.1 manual workflow), do we (a) append a "Skills installed by agentic" section, (b) leave it alone and document the skills elsewhere, or (c) create a sibling file? cc-sdd does (a). Recommend (a) but confirm with Alexandre.
- **Naming inside Codex:** cc-sdd's docs render skill invocations as `$kiro-name` (dollar-sign), but Codex's own slash command menu is opened with `/`. Whether this is a markdown convention or a real Codex syntax detail — to confirm during implementation by trying both.
- **Telemetry:** none for now. If we ever need to know which skills get used, that is a separate ADR.
- **Updates:** how does `agentic init` behave on a project that already has older versions of the skills? Likely: detect installed version, offer update, preserve customizations. Detail in chunk 4.
